## 2. System architecture (designed)

### 2.1 Shape

A responsive web application with a single backend aggregating several external data sources plus student-supplied data. No institutional system integration.

```
  Student browser
        |
  Web application (responsive)
        |
  Application backend
    |        |            |              |
 Auth    Campus data   Student data   Extraction
 module   adapters      store          service
    |        |            |              |
  Email   PRT API     Encrypted      PDF parse +
  OTP     Public web   per-user      LLM extract
          Mountain     records
          Line
```

### 2.2 Data sources and access model

Every source was selected because it requires no institutional approval. This constraint is the project's defining design decision.

| Source | Data | Access | Verified |
|---|---|---|---|
| WVU PRT Status API | Live PRT operating status | Public JSON endpoint, `prtstatus.wvu.edu/api/[unix-timestamp]/?format=json`, no auth, no rate limit | Discontinued November 2026. No replacement source identified. |
| Blackboard calendar export | Assignment due dates, course events | Read-only share link generated by the student from their own account | Not measured, see section 5 |
| Syllabus PDFs | Assignments, dates, grade weights | Uploaded by the student | Not measured, see section 5 |
| Public WVU web data | Academic calendar, hours, alerts | Public retrieval | Available |
| Mountain Line | Transit schedules | Public source | Available |
| Student input | Grades, goals, preferences | Application input | N/A |

**Explicitly excluded:** Banner, STAR, DegreeWorks, and any institutional API. The academic risk indicator was redesigned to run on syllabus weights, deadline proximity, completion status, and self-entered grades precisely so that no institutional credential is required.

### 2.3 Authentication design

**Pilot:** passwordless email sign-in restricted to `@mix.wvu.edu`. One-time link or code, short expiry, single use, no password storage anywhere in the system.

**Production:** WVU SSO through Okta. A student at an adopting institution would never create an account.

**The design decision that matters:** authentication is isolated behind a swappable module so SSO can replace email sign-in without touching the rest of the application. Recorded as an architecture decision record.

**Open finding:** `@mix.wvu.edu` appears to be shared across WVU System institutions, which means the email domain alone does not identify a student's campus. This matters for any future multi-institution work and is unverified. See section 5.

### 2.4 Privacy and security design

- Data stored: student-supplied calendar link, uploaded syllabi and extracted items, self-entered grades and goals, institution identifier
- Encryption in transit and at rest; calendar share links stored encrypted
- No passwords stored
- No data shared with third parties
- Consent captured before a calendar link or syllabus is accepted, recorded with a timestamp, withdrawable
- Account and data deletion honored within 24 hours, including uploaded files

**FERPA position:** the system holds student-supplied data about the student, not institutional education records. That distinction is the basis of the position and would require institutional legal review before any adoption.

### 2.5 Accessibility

WCAG 2.1 Level AA is treated as a procurement gate, not a feature. The design calls for an automated `axe-core` scan in CI failing the build on serious or critical violations, plus manual keyboard-only and screen reader passes. Automated tooling catches roughly 30 to 40 percent of real accessibility issues, which is why the manual passes are in the plan rather than optional.

## 4. Governance and how decisions were made

**Change control.** Scope changes are raised as an issue labeled `scope-change`, assessed by the PM for impact on schedule and capacity, and decided by the team acting as a Change Control Board. Approval requires naming what gets cut to pay for it.

**The one change request received.** CR-001 from the Vice Provost: extend WVU Nexus across all WVU System institutions with a dynamic interface per campus. Estimated at 36 story points against a backlog already 40 to 50 points over capacity. **Decision: Defer**, with a 5-point architectural provision approved so the eventual work would be an extension rather than a rewrite. Full analysis in `docs/IMPACT-ASSESSMENT.md`.

**Board conventions.** Status reflects reality rather than intention. WIP limited to 3 items in progress and 2 in QA. Done requires the Definition of Done checklist to be met, not just a closed issue. Work not on the board is invisible at peer evaluation.

## 5. Open items a future team inherits

These are the things that are genuinely unknown, stated so nobody rediscovers them the hard way.

| # | Open item | Why it matters |
|---|---|---|
| 1 | Blackboard calendar coverage was never measured | The deadline tracking epic assumes exports carry most assignments. If coverage is low, syllabus extraction becomes the primary input rather than the supplement, which changes the product's center of gravity. |
| 2 | Syllabus extraction accuracy was never measured | The entire syllabus epic rests on this. A go or no-go decision was supposed to follow a timeboxed spike. The spike was closed without execution and the issue records that openly. |
| 3 | WVU data permissions were never confirmed | A previous third-party PRT application was shut down. The reason was never established, and no response was received from Transportation and Parking or ITS. |
| 4 | Institution identification from email domain | If `@mix.wvu.edu` is shared system-wide, multi-institution support needs campus selection at onboarding or a directory lookup. |
| 5 | Data availability at Potomac State and WVU Tech | Unknown whether those campuses publish the equivalent public data. A dynamic interface showing those students an empty product would be worse than not supporting them. |

**Recommended first action for any successor team:** run items 1 and 2 as timeboxed spikes before writing application code. They are cheap, they take days, and they determine whether the two highest-value epics are viable as designed.

## 6. If the project continues

**Deferred scope:** CR-001 multi-institution support, 31 points remaining after the approved architectural provision, decomposed into issues #27, #29, #30, #31, #32, #33. Retained in the backlog so the deferral stays visible.

**The adoption path, in priority order:**

1. Real pilot users with reported usage numbers. Twenty students actually using it outweighs any projection.
2. Documented WCAG 2.1 AA conformance. It is a procurement gate for university software.
3. A privacy and security design that survives an ITS review.
4. A named champion inside the university. The Vice Provost's unsolicited interest in CR-001 is the strongest signal the project received and that relationship is worth maintaining.
